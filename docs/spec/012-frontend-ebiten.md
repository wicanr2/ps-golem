# 012 Ebiten 視窗前端

狀態：`READY`

## 1. 為什麼

M4 的驗收是玩家走到第一個存檔點存檔（`001` §4）。序章要打德古拉，之後操作阿魯卡德走到存檔室，
用按鍵腳本盲打不實際，需要人能即時看畫面、操作。前端只消費核心（`001` §2）：
讀畫面、寫手把按鍵、存記憶卡，不改機器狀態的推進方式。

## 2. 執行檔

`cmd/psgolem`：

```
psgolem [-bios <BIOS>] [-cue <cue>] [-card <記憶卡檔>] [-scale N]
```

`-bios`、`-cue` 可以省略，改用設定檔或拖放（§9）。

- `-card` 省略時用 `<使用者設定目錄>/ps-golem/<光碟開機檔名>.mcd`
  （Go `os.UserConfigDir`；本案例檔名 `SLPM_860.23.mcd`）。存檔屬玩家資料，不寫進素材目錄或 repo。
- `-scale` 是起始視窗倍率，預設 3。

## 3. 時間

- 首次模擬須等視窗至少完成一次 Draw，並等已開啟的音訊後端就緒；Ebiten 在首次交換畫面後才顯示視窗，不能以首次 Update 當作可見確認。靜音模式不等待音訊，避免顯示初始化期間遊戲先行、音訊積壓。尚未起跑便關窗也必須能正常收尾。
- 機器在自己的 goroutine 推進（`frontend/ebiten/emu.go`），每次跑到下一次 VBlank
  （`RunUntilField(field+1)`，上限 2 個 field 的週期數，防止顯示關閉時卡住）。
  Ebiten 的 `Update`／`Draw` 只交換按鍵與取最新畫面，畫面繪製的耗時不佔模擬時間。
- 步調：模擬的週期數除以 33,868,800 Hz 換成實際時間，模擬超前就等待。SPU 每 768 週期出一組取樣，
  所以聲音的產出速度與播放速度一致。落後實際時間超過 100 ms 時把基準移到現在，不追趕。
- 機器狀態只由模擬 goroutine 改。按鍵在每個 field 開始前套用；按鍵腳本（`-press`）以 field 計，
  重播結果與執行速度無關。
- 機器的時間只由 CPU 週期決定（`001` §3.1）；前端不跳 field、不補 field。
  模擬比實機慢時，遊戲整體變慢；不改變任何決定性狀態。
- `-stats` 每 600 個 field 印出視窗 FPS、每秒模擬 field、相對實機週期速度、模擬與畫面輸出耗時、發布數、缺少／丟棄的立體聲取樣組數與基準重設次數。音訊缺樣是播放器要求資料時佇列不足的組數，不把原本的靜音誤算成缺樣。
- 非同步的耗時另列 `core_avg` 與 `hd_wait_avg`，分別量測推進一場與等待上一個影子要求的牆鐘時間。CPU 剖析中鎖操作取樣少，不能推定等待時間少。
- 呈現端只要求最新畫面。慢視窗尚未消費前一張時，可省略中間 field 的 RGB 轉換與發布；所有 field、GPU 命令、音訊、輸入與存檔仍完整執行。首次畫面與指定 `-fields` 的終點必須發布。此為既有「只取最新畫面」契約的效能實作，不降低畫質或改變模擬時間。
- HD 輸出依 `016-hd-output` §8.1 採一場有界非同步呈現。暫停、終點及停止排空未完成要求；未掛 HD 仍同步。緩衝只影響呈現排程，不改模擬時間或輸入位置。
- 效能現況（2026-10-17，Core Ultra 7 165U，主機另有其他工作）：無頭模擬固定在 P 核心
  （`PSGOLEM_CPUSET=0-3`、`GOMAXPROCS=2`，取樣期間 P 核心平均 1.77 GHz），序章遊玩段（field 4800–7200）
  每個 field 9–14 ms，低於 16.7 ms。KONAMI 動畫段（field 1800–2400）在兩次量測為 10–42 ms，期間 P 核心時脈在 1.2–1.8 GHz 之間變動，可能超過預算。
  遊玩段的耗時約 72% 在 CPU 直譯、18% 在 GPU 點陣化，GC 不顯著。被排到效率核心或時脈受限時會落後實際時間。
- 量測方法：比較改動前後用同一段 field、固定核心、交錯執行、取 CPU 時間（rusage）的最小值；
  牆鐘時間與 xvfb 下的 FPS 受主機負載與軟體 OpenGL 影響，不作為效能數字。

## 4. 畫面

- `Draw` 取模擬 goroutine 最新完成的畫面（`GPU.OutputScreenInto`，`007` §8、`016`）寫進 Ebiten 影像，
  依 4:3 顯示比例縮放到視窗中央，多出的邊填黑。縮放用最近鄰；HD 濾鏡另由 HD 規格處理。
- 畫面編號與視窗大小都沒變時 `Draw` 直接返回（`SetScreenClearedEveryFrame(false)` 保留上一次的畫面），
  高更新率螢幕或沒有垂直同步的顯示環境不會重複縮放同一張畫面。
- 畫面尺寸改變（遊戲切換解析度、24 位元動畫）時重建影像。

## 5. 輸入

每次 `Update` 先讀輸入，再跑機器，按鍵寫進 `machine.Pad1.Buttons`。

| 手把 | 鍵盤 | Ebiten 標準手把 |
|---|---|---|
| 十字鍵 | 方向鍵 | 左側十字鍵 |
| ✕ | `Z` | RightBottom |
| ○ | `X` | RightRight |
| □ | `A` | RightLeft |
| △ | `S` | RightTop |
| L1／R1 | `Q`／`W` | FrontTopLeft／FrontTopRight |
| L2／R2 | `1`／`3` | FrontBottomLeft／FrontBottomRight |
| START | `Enter` | CenterRight |
| SELECT | `Backspace` | CenterLeft |

鍵盤與所有已連接的標準手把取聯集。

## 6. 記憶卡

- 啟動時檔案存在就載入（`010` §4），否則用空白卡。
- 卡片 `Dirty` 且距最後一次寫入（frame 寫入完成）超過 60 個 field，寫回檔案並清掉 `Dirty`；
  關閉視窗時再檢查一次。寫檔先寫暫存檔再改名，避免寫到一半中斷。

## 7. 驗收

| 項目 | 判準 |
|---|---|
| 按鍵對應、顯示比例 | 單元測試（純函式，不開視窗） |
| 視窗啟動 | 容器內 `xvfb-run` 跑 `psgolem -frames N -screenshot <png>`：跑 N 次 `Update` 後存下 Ebiten 實際畫出的畫面並結束；與 `psexe -screen` 在同一 field 的畫面一致 |
| 實際遊玩 | 玩家在主機上執行，從開機玩到存檔點存檔（M4 驗收，由玩家確認） |

`-frames`、`-screenshot` 只給驗收與除錯用。`-mute` 不開音訊裝置（容器內沒有音效卡時用）。
`-press <腳本>` 以按鍵腳本（`010`，與 `psexe -press` 同格式，解析在 `internal/padscript`）取代鍵盤與手把，
`-fields N` 跑到第 N 次 VBlank 就存記憶卡、截圖並結束；結束前必須確認最後一張畫面實際完成 Draw，不能假設下一次 Update 之前必定有 Draw。只在最後 Draw 複製截圖，避免每場複製驗收畫面而干擾速度。兩者用來讓發行包的視窗執行檔重播整段遊玩。

## 8. 聲音

`013` §5：每次 `Update` 跑完一個 field 後取走 SPU 的取樣，送進 44.1 kHz 播放器（Ebiten `audio`，緩衝 60 毫秒）。
排隊超過約 0.25 秒就丟掉最舊的；不夠時補靜音。

## 9. 啟動與設定檔

Windows、macOS 的玩家通常用滑鼠雙擊開啟，沒有命令列參數，所以 BIOS 與光碟的位置要能記住。

- 設定檔：`<使用者設定目錄>/ps-golem/settings.json`，內容 `{"bios": "<路徑>", "cue": "<路徑>"}`。
- 決定路徑的順序：命令列參數優先，沒給的項目取設定檔。
- 可攜設定檔與自動尋找 BIOS、光碟見 `005` §8.1；有可攜設定檔時，本節的設定檔換成它。
- 音訊裝置開不起來時印出警告、改為靜音照常執行（雙擊開啟看不到錯誤訊息）。
- 兩個路徑都有，且 BIOS 與光碟都開得起來，就開機；成功開機後把這組路徑寫回設定檔。
- 缺任何一項，或開啟失敗，視窗顯示設定畫面：列出目前的 BIOS、cue 與錯誤訊息，
  提示把檔案拖進視窗。畫面文字只用 ASCII（Ebiten 內建的除錯字型沒有中文字）。
- 拖進的檔案依序判斷：副檔名 `.cue`（不分大小寫）當光碟；大小正好 512 KiB 當 BIOS；其他忽略。
  兩項齊了就照上一條開機。
- 拖放的實際路徑取自 Ebiten `DroppedFiles` 開出的 `*os.File` 的 `Name()`（Ebiten v2.9.9
  `internal/file/file_notjs.go` 以 `os.Open` 開實際路徑）；拿不到實際路徑的檔案忽略。

## 10. 驗收結果（2026-10-15）

- 按鍵對應、顯示比例、記憶卡等待安靜後存檔：`frontend/ebiten` 單元測試通過（`xvfb-run`）。
- 視窗啟動：容器內 `xvfb-run psgolem -frames 2000`（960×720 視窗）與 `psexe -fields 2000 -screen`
  比對，依 4:3 置中規則對回 320×240 後 0 像素不同（KONAMI 標誌畫面）。
- 實際遊玩：待玩家確認。
- 設定畫面（2026-10-16）：`dropKind`、`asciiPath` 單元測試通過；容器內不帶參數開機顯示設定畫面，
  路徑錯誤時列出錯誤；以參數開機後寫入 `settings.json`，再不帶參數開機，第 2000 次 `Update` 與 `psexe` 0 像素不同。
  拖放在 xvfb 下無法模擬，由玩家在主機上確認。

## 11. 保存輸出解析度（READY）

使用者於2026-10-20要求繪製層突破PS1解析度，至少1920×1080，並確認沿用目前美術。
此節只新增可保存的呈現尺寸，不改遊戲座標、寬螢幕規則、模擬狀態或既有HD倍率。

| 項目 | 契約 |
|---|---|
| CLI及設定 | `psgolem -resolution 1920x1080`；保存於settings.json的`resolution`字串，下次無參數啟動沿用。命令列明確指定優先，`-resolution auto`清除尺寸，回到既有`-scale`規則。 |
| 格式與範圍 | 寬×高以ASCII的x分隔，不分大小寫，正規化十進位；寬320–7680、高240–4320。兩維須同時有效，錯誤在開機前回報。空設定保持舊行為。 |
| 呈現比例 | 明確尺寸只控制起始視窗。原版依4:3置中，1920×1080時畫面1440×1080；既有寬螢幕模式依16:9填滿。仍允許玩家調整視窗，不拉伸內容。 |
| 內部解析度 | `-hd`仍獨立保存，現有1／2／4／8倍來自016。輸出1920×1080不代表所有來源有1080p細節；2D舊圖與MDEC仍受來源限制。月下256×240的8倍畫面為2048×1920，再依顯示比例取樣；較高倍率的速度需另驗。 |
| 實作範圍 | cmd/psgolem/resolution.go解析尺寸，main.go保存設定，frontend/ebiten/game.go只設定視窗大小；resolution_test.go及既有frontend_test.go核對。不得由resolution自動開啟寬螢幕、GPU、PGXP或改變hd，避免把顯示偏好變成遊戲修改。 |
| 驗收 | 解析／優先序／清除／非法範圍、設定保存與其他設定保持；1080p原版及寬螢幕置中；實際視窗截圖1920×1080與獨立重開沿用。真機跨平台、正常全遊戲與速度另列，不由尺寸測試外推。 |

來源為本repo現行game.go的SetWindowSize、Layout與layout.go的fit／fitWide，以及016的NewShadow倍率契約。
中文字HD的字形識別、製作與小型PNG另由私人素材repo docs/assets-catalog.md的中文字HD節追蹤，不在通用前端猜譯文。
